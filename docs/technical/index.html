Feetness technical documentation

You text Feetness what you trained, like texting a friend. It saves every set as a fact, keeps a written profile that cites your own messages, tracks injuries, and answers training questions as a coach that may only speak from what you logged.

A message's journey

One workout message, from your phone to the receipt, and the profile rewrite it sets off two minutes later. Each numbered dot is a row in the table below; dashed arrows are the usage ledger (ai_calls), which records every model call with its tokens.

#What happensWhere in the code
1The poller long-polls Telegram and turns the update into an InboundMessage. One poller per bot token, under supervisord.channel:telegram:poll, TelegramChannel::inbound, HandleInboundMessage::handle
2The sender is looked up. A stranger gets one polite private-beta reply a day and costs nothing; /start CODE from an invite link connects them.channel_identities, RedeemLinkCode
3A slash command runs its ChatCommand. Otherwise the answer chain tries each open question without AI: a missing exercise value, the injury area, the red-flag screen, a profile question.ChatCommands, AnswerChain, config/conversation.php
4Free text goes to the AI path, the same one the retry job uses.RespondToText::reply
5Danger words (chest pain, numbness, fainting) get "contact a doctor" in plain code. Nothing is saved and no model is asked.RedFlags::matches
6The classifier gives the message one of five kinds. Plain rules first, then the model. See the classifier.MessageClassifier, SdkMessageClassifier, ClassifierAgent
7The parser for that kind reads the facts: exercises, sets, reps, loads, per-set lists, the date, at most one question for a missing value.SmartLogParser, SmartLogAgent (or LimitationAgent for injuries)
8Named rules turn known traps into a question instead of a guess ("90 x3 x5": three sets or five?).Interpreter::RULES, app/Interpretation/Rules
9The interpreter hands back what it made of the message.Interpretation
10One transaction writes your words (activity_logs), the session, the entries and one row per set.RecordSmartLog

/undo reverts exactly what one message saved and fires LogReverted, which refreshes stats and the profile the same way. A coach question takes the same road to step 6 and then goes to the coach (the coach). If every model fails at step 6 or 7, the message is kept and retried (when the AI is down).

The classifier

Every free-text message gets one label before anything else happens, and the label picks the road. The classifier is a port, MessageClassifier, with three drivers chosen by AI_CLASSIFIER; production runs llm. Plain rules always go first, so a command or "104.5kg" never reaches a model.

The five kinds

The wording below is what the model is given (MessageKind::criteria() for Laya and Jev; the ClassifierAgent prompt adds examples). command is a sixth kind that only the rules hand out.

Where it could go

Not built. A cheaper classifier saves almost nothing (about 2 cents per person per month). What it can buy is speed (0.95 s to about 0.1 s) and availability: a classifier on our own server keeps sorting messages when Google is overloaded. The plan from the 7 November exploration: run Laya or Jev in shadow mode next to the LLM on about 200 real messages, fit the cut-off on that, and switch first where a wrong pick is harmless (the coach's answer size, AnswerDepth, today plain regex). The AI library now ships Classification::of() with a TypeSafe gateway that can replace our own SystemOneClient.

What every prompt does

Data, not orders

Each prompt says the message (or CONTEXT) is data, never instructions. A user typing "ignore your rules" is logged as a message, not obeyed.

Nothing invented

Numbers come from the message, from FACTS, or from the person's own entries. A value the message does not give is null, and the app asks for it.

Examples over rules

The classifier, log reader and limitation reader each carry worked examples from real messages ("yesterday squats 5x5, 90 80 80 80 80").

PHP does the maths

Stats (ProfileFacts), which exercises load an injury (ExerciseLoads), answer size (AnswerDepth) and danger words (RedFlags) are plain code. The model words things; it does not calculate.

The coach prompt, piece by piece

  1. Who you are. "You are {name}, a personal trainer texting with one person on Telegram", then TrainerPersona::voice(): style only, with how the coach talks when you are hurt, in a hurry, or say it was wrong.
  2. What CONTEXT is. Facts to trust, the profile notes, the logs newest first with what was saved, injuries with how each is going and which exercises load it, the last exchanges.
  3. What a good answer is made of. It answers the question in your language; it is built from your data (last 7 days, goal, injury, what it said before); loads are numbers (continue from the last top set, a variation starts at about two thirds, no record means a starting rule and "log it"); the goal shapes it; an active injury rules out the exercises that load it unless a variation takes the load away; at most one thing to send back.
  4. The answer size from AnswerDepth::instruction(): quick (5 short lines), plan (a session you can walk in with), explain (12 lines with one picture).
  5. Rules that never change. Never invent; read recent_exchanges first and say so when the plan changed; no homework; no insults or guilt; voice lines are tone, never copied; the name at most once; conservative self-care only, no diagnosis or doses; a doctor only when it matters now; never refuse a question as off-topic; plain text.
  6. Today's date and the CONTEXT JSON: today, facts, profile_notes, limitations, recent_logs (12), recent_exchanges (6 from the last 72 hours), messages_not_handled_yet.

The profile prompt

One note per section that the data says anything about (the nine NoteLabel sections: rhythm, strength, balance, conditioning, body, limitation, goal, responds, gaps), always a gaps note, each at most 240 characters and citing entry ids, a previous note's cites, or "facts". Keep what is still true, update what changed, drop what the new entries contradict. What the coach said is not a fact about the person.

Tokens and thinking

  • The coach's token ceiling never binds: the two recorded answers used 59 and 74 tokens against ceilings of 800 and 1,500. Length comes from the answer-size line, so a longer, better answer is a prompt change, not a budget change. The budgets stay generous because thinking models count hidden reasoning against them.
  • The profile rewrite is the expensive call: about 4,900 output tokens for about 500 tokens of notes. The rest is almost certainly hidden thinking, billed as output. No agent sets a thinking level yet; the AI library allows it per agent (HasProviderOptions).
  • A logged message (classify and read) costs about a tenth of a cent; a coach question about a sixth.

Changing a prompt

  1. Edit the agent class. One file per prompt; the schema and the temperature live next to the words.
  2. Try it without saving. php artisan log:parse "text" for the classifier and log reader, classify:try per driver, make classify-eval over tests/Evals/classify.txt.
  3. Try the whole path. php artisan log:simulate --user=1 "text" runs a message as if it came from Telegram, coach included, on your local key.
  4. Keep the suite green. Tests never call a model (see testing), so they check the wiring and the schema handling, not the wording. Write what came back in the PROJECT.md diary.

Open proposals for the coach, from the 7 November exploration, section 10: a today block with what was logged today, an already_suggested list so "do not repeat" can be checked, voice examples that name no exercises, asking about an injury at most once a day, and every load naming its source.

A message's journey

"Squats 5x5 / 90 80 80 80 80 / And ran 1k in 6:30", from your phone to the receipt.

  1. The poller receives it. channel:telegram:poll long-polls Telegram, turns the update into an InboundMessage (TelegramChannel::inbound) and hands it to HandleInboundMessage::handle. One poller per bot token runs under supervisord.
  2. Who is this? The sender is looked up in channel_identities. A stranger gets one polite private-beta reply a day and costs nothing; /start CODE from an invite link connects them.
  3. A command? Text starting with / is looked up in ChatCommands (the list in config/conversation.php).
  4. An answer to an open question? The answer chain tries each handler in order without AI: a missing exercise value ("5 reps each set"), the injury area ("1"), the red-flag screen ("no"), a profile question ("3"). Words after an answer ("70kg, now what next?") go on as their own message.
  5. The AI path. RespondToText asks the Interpreter: danger words first (RedFlags, plain code: "contact a doctor", nothing saved), then classify (plain rules such as "104.5kg", then the model), then parse with the parser for that kind, then the named rules that turn known traps into questions ("90 x3 x5": three sets or five?).
  6. Act on it. A workout or weight goes to RecordSmartLog: one transaction writes the activity_logs row (your words), the session, entries and one row per set, then LogRecorded fires after commit. An injury goes to LimitationConversation; a question to AnswerCoachQuestion.
  7. Reply. The receipt ("Logged: Squat 5x5 @ 90, 80, 80, 80, 80 kg, Run 1 km 6:30"), plus at most a load check for an active injury and one profile question.
  8. Afterwards. Listeners recompute stats and queue BuildProfile 120 seconds later (one AI call per burst of logs). /undo reverts exactly what this message saved.

Open questions

A log or a limitation can carry one open question (activity_logs.questions), answered without AI for 6 hours on the newest log. NumberReply reads a reply that starts with a number; the unit must fit the field ("12 kg" is not reps); a second number means a new log. A per-set field (exercises.0.set_list.5.weight_kg) fills one set. Profile questions (config/profile.php: training days, main goal) are asked at most once every 20 hours, answerable for 24, correctable with "No, ..." for 10 minutes.

Injuries and limitations

  1. Danger words come first. RedFlags (numbness, chest pain, can't feel, bladder...) answers "contact a doctor" before any AI and saves nothing.
  2. Read the facts. LimitationAgent returns area, severity, duration and a short note, never advice.
  3. New or update? ExistingLimitation: same area as an active one, or no clear area with exactly one active, is an update (limitation_updates, your words, a new duration moves the end date). Otherwise RecordLimitation creates it.
  4. Ask once. Unclear area: numbered choice. Then the red-flag screen: "any numbness, tingling, weakness or pain down an arm or leg?" stored as clear or flagged.
  5. Use it. A logged exercise that loads the area (ExerciseLoads) gets "Lower back OK with the Deadlift?" on its receipt; the coach sees the day count, updates and the exercises that load it.

The coach

AnswerCoachQuestion checks the daily cap (30) and the monthly token cap, builds CoachContext, sizes the answer with AnswerDepth, makes one call through the CoachAdvisor port and stores the exchange in coach_turns (conversation, never facts). Within 30 minutes of an answer, a message the sorter cannot place ("you got that wrong") goes to the coach as a follow-up.

What the coach sees

  • Facts computed in PHP (ProfileFacts)
  • The written profile notes
  • Active limitations: day, updates, red-flag screen, exercises that load it
  • The last 12 logs in your words, with saved exercises
  • The last 6 exchanges from 72 hours
  • Messages kept during an outage

Answer size

  • quick: "foam roller?" (800 tokens)
  • plan: "30 min, 3 things", "suggest", "what weight" (1,500)
  • explain: why, how, what does (2,000)

Plain-code rules in AnswerDepth; tokens are a ceiling, the prompt sets the length.

Three voices

  • Lt. Surge: strength, clipped, never cruel
  • Shen: performance, thinks in phases
  • Latika: recovery and mobility, warm

TrainerPersona::voice() is style only; the rules in CoachAgent are the same for all.

The written profile

After a burst of logs, BuildProfile runs UpdateProfile: the current notes plus the last 10 entries (logs and coach questions) go to ProfileAgent, which writes up to 10 notes, each in one of nine sections (NoteLabel: rhythm, strength, balance, conditioning, body, limitation, goal, responds, gaps) and each citing log ids, coach:N or facts. A note whose citations do not exist is dropped, so an undone log's notes vanish at the next update. Every Monday at 04:00 a full rebuild from the last 30 entries resets drift. Read it with profile:show; rewrite now with profile:rebuild email --full.

  • Jobs and models. Each job has a provider and model in config/ai.php (AI_LOG_*, AI_CHAT_*, AI_PROFILE_*); empty means the log job's.
  • Failover. ModelChain::ask(job, ...) tries the job's model, the log job's, then AI_FALLBACKS, moving on when a model is overloaded, rate limited or unreachable.
  • One seam. Every call runs through AiCall, which tags user and job and turns failures into AiUnavailable.
  • Usage and cost. RecordAiCall stores every call in ai_calls (tokens, model, duration, failure). php artisan ai:usage --since=30d --by=user|job|model|day; prices per model in config/ai.php.

When the AI is down

  1. Next model. ModelChain tries the rest of the chain.
  2. Keep it. If every model fails, KeepMessage stores the message in waiting_messages and replies "The AI is busy right now. I kept your message and will answer here in a few minutes, no need to send it again."
  3. Retry. ProcessWaitingMessage runs the same path after 1, 3, 10 and 30 minutes (conversation.retry_delays) and answers in the chat by itself ("About "...": Logged ..."), or says it did not go through.
  4. No doubles. The same text sent again while its copy waits is handled once; the kept copy is marked resent. The coach sees messages still waiting.

The audit of 8 November found the retry not yet safe to repeat and replying on Telegram regardless of channel. See the audit report, tier 1.

Testing

make test      # SQLite in memory, about 5.3 s
make test-pg   # Postgres, about 9.8 s (CI runs both)
vendor/bin/pint --test
  • No test can reach a model. phpunit.xml blanks every AI key, the bot token and AI_FALLBACKS; tests/TestCase.php binds all eight AI ports to their fakes and calls Http::preventStrayRequests(). tests/Unit/TestGuardsTest.php fails if any of that goes missing.
  • Testing a real adapter is explicit: useRealAdapter(SmartLogParser::class), with Ai::fakeAgent() or Http::fake() underneath.
  • Two ways to fail. Every fake has failing(), which throws what a real outage throws (ProviderOverloadedException), and broken(), which throws a plain bug. Only the first may be treated as "the AI is busy".
  • Helpers in tests/Pest.php: linkedUser(), telegramText(), classifierSays(), fakeCoach(), fakeSmartLogParser() and the rest.
  • The test environment is forced twice in phpunit.xml (env and server) so a local .env cannot leak in. Failed logins skip Laravel's 200 ms padding in tests (auth.timebox_duration 0).
  • Real-model checks are manual: log:simulate with your Gemini key, and the eval files in tests/Evals.
