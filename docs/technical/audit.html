Adversarial audit · code and tests · 8 November 2026

Feetness audit report

Five independent reviewers tried to prove the code and the tests wrong. The architecture holds; the bugs cluster in a few places, and the tests miss them because they only ever send the input each piece expects.

Verdict

Code

Not yet

for testers. Twelve tier-1 findings, about two focused days. The design itself is sound.

Tests

310 pass

but none sends the message a greedy handler would steal; two tests treat a bug as the specification.

Speed

8.5 s

SQLite (13 s Postgres). 39% of it is four failed-login tests waiting on purpose; fixable to about 5 s.

Isolation

0 requests

to any AI provider during a full run, measured with a spy server. Safe by care, not by a guard.

The one-line summary. The way the code is organised is right; the places where a message is claimed by the wrong handler, and the retry path built on 8 November, are wrong. Write the missing tests from the reproductions first, then fix, and the suite becomes the guard it should be.

Dependencies pointing the wrong way

Domain code tags AI calls with adapter class names; Channels and Conversation use each other; no channel registry by provider; an adapter's model is a side channel.

Before WhatsApp.

Open questions as a type

Every handler re-derives "is this mine" from field strings; a newer log orphans an older question.

Indexes and queries

Postgres has no index on most foreign keys; sets are re-queried when loaded; records load every session ever, several times per request.

Smaller things

Fourteen items, schedule when convenient
  • Dates and daily caps are UTC: a log at 00:30 Amsterdam lands on the previous day.
  • /better knee heals the newest injury, not the knee.
  • Undoing a limitation update leaves its new end date.
  • "3x5" or "3 sets of 5" is not taken as the answer to "3 sets of 5 or 5 sets of 3?".
  • A kept message is handled after newer ones; /undo can remove the wrong log.
  • The scheduler loop drifts and can skip the weekly profile rebuild; use schedule:work.
  • A missing APP_KEY in production is silently replaced; fail instead.
  • The sign-in token is in the URL query; a fragment keeps it out of server logs.
  • Query errors and the poller's reply excerpts can put injury text in logs.
  • One hung model call blocks the poller for everyone (60 s default timeout).
  • Duplications: number formatting four times, "skip" four times, sanity limits three times with different values.
  • Stale docblocks (User::waitingMessages, RecordSmartLog, UpdateUserStats).
  • Email case is not normalised on login and profile update; Postgres uniqueness is case-sensitive.
  • Unpinned build inputs; expose_php on.

What is good

AI behind ports

Every live AI call has a port and a fake; a full run made zero provider requests.

Write actions

One transaction, setRelation instead of re-querying, the event after commit.

Easy to extend

A command or an answer handler is one class and one config line; the Telegram menu follows.

Facts stay facts

The profile's citation check, named rules, numbers in PHP, model output clamped before saving.

Security basics

php-fpm on loopback with a build check, hashed single-use codes with locks, owner-scoped queries, closed registration.

Strength

Two tests enshrine bugs. AiUsageTest:65-72 expects a plain RuntimeException to come out as AiUnavailable, which is exactly the "every error is an outage" bug. InterpreterTest:39-49 pins "coaches coming soon" for the app door. And every fake's failing() throws RuntimeException, so the ten outage tests depend on that bug: fixing AiCall turns them red although nothing is wrong.

  • The main fake does not look like the real adapter. FakeSmartLogParser returns the raw payload: no set_list, old meal fields, unclipped questions. The real adapter normalises all of that, so a bug between the adapter and RecordSmartLog is invisible to every chat test.
  • Assertions that pass when the behaviour breaks. "Caps adherence at 100" never reaches the cap (five sessions on one day is 33%). "Waits longer" never checks the delay. "12 kg is not reps" only checks what did not happen. "Without touching the database" only checks the status code.
  • Retry tests bypass the real wiring. The chat channel is injected by hand, so the Telegram-only binding never runs, and the fake channel cannot fail.

Redundancy

  • The same fact through several doors: the trainer outage message three times (all legacy), the log outage twice, the weekly score from four doors, "a stranger is never parsed" twice.
  • Candidates for one dataset test: the owner-scoped 404s (five files) and three copies of the Laya response helper.
  • app(HandleInboundMessage::class)->handle(telegramText(...)) appears 47 times; a say() helper would make every chat test read like the conversation.
  • Nineteen global helper functions live inside test files; one name clash stops the whole run. Unused: fakeNutritionParser(), toBeOne, and the failing() of the limitation parser and classifier fakes (so those two outage paths are untested).

Fixing the tests

The ten most valuable missing tests

  1. With a profile question open (and within 10 minutes of a correction), real workout and injury texts are logged and the profile stays unchanged.
  2. With "Where exactly?" open, "shoulder press 3x10 30kg" is logged and the area stays empty; only a bare number or area name is taken.
  3. A pulled hamstring with an active back injury creates a second injury; the back's end date is unchanged.
  4. With a red-flag screen open, a "yes" after a coach question does not flag the injury.
  5. A resend during the retry's AI call is logged once; a failed send keeps the reply retryable without a second log; exhausted tries end as failed.
  6. A kept message from the simulator never calls Telegram; a Telegram one replies to the right chat.
  7. A plain bug in an adapter is reported and not kept; overload and connection errors keep the message.
  8. Answering an open weight, area or red-flag question fires the profile refresh and writes nothing if a step throws.
  9. channel:unlink deletes the person's tokens; an expired token gets 401.
  10. A classifier or limitation-parser outage on the chat path keeps the message.

Structure

Feature and Unit are split by "needs the database", not by what is tested. Grouping by journey would make the suite read as a specification: Chat/Logging, Chat/OpenQuestions, Chat/Limitations, Chat/Coach, Chat/Retries, AppApi, Adapters, Tools.

Order of work

  1. Test guards first (an hour). Blank the AI keys, bind every fake, block stray HTTP, set the login timebox to 0 in tests. Switch the fakes' failing() to real availability errors and add a separate broken().
  2. Handlers take only whole answers (half a day). Write missing tests 1 to 4 from the reproductions, watch them fail, fix the profile, area and red-flag handlers and the "other" injury.
  3. A safe retry (a day). Tests 5 to 7 and 10, then claim the row, send separately, a failed() handler, the channel by provider, AiCall wrapping only availability errors, and rewrite AiUsageTest:65.
  4. Production hardening (half a day). pcntl, schedule:work, worker timeouts, token expiry and revoke on unlink (test 9), the nutrition route gone, local ports on 127.0.0.1, answers in transactions with the event (test 8).
  5. Clean-up round. Delete the legacy code with its ~34 tests, fix the weak assertions, add the three adapter contract tests, indexes.
  6. Then the features. Exercise catalogue and strength calculator before the body map and plans; the classifier seam before the shadow run; the channel registry before WhatsApp; one outcome type before the app writes.
