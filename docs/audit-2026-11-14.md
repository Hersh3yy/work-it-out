1. Double log. `RespondToText::reply` records the log, then `thenTheCoach` calls the coach. When the coach throws `AiUnavailable`, `HandleInboundMessage::respondWithAi` keeps the whole text, and `ProcessWaitingMessage` later replays it through `reply`, which records the log again. "bench 3x5 70, what next?" during a coach outage doubles the sets and the volume: the 7 Nov incident the kept-message feature exists to stop. The limitation path (`RespondToText.php:47`) has the same shape. `LogAndAskTest` covers only the happy path and `KeptMessagesTest` only a parser outage. Fix: a test with a working parser and a failing coach through `HandleInboundMessage` (one activity_log, no waiting_messages row), then catch `AiUnavailable` inside `thenTheCoach` and add a "the coach is busy, ask again" line.
2. Red flags. `freeText` runs the answer chain before anything reaches `Interpreter`, where `RedFlags` lives. With an area question open, `LimitationChoiceAnswer` reads "1 hour ago my leg went numb" as option 1 and returns an answer with no follow-up, so the see-a-doctor reply never comes. Fix: check `RedFlags::matches` at the top of `freeText`, and test a red-flag message against each open-question kind. The root cause, greedy answer handlers, is 2026-11-08 tier 1 items 1 to 3.
3. CI. The `composer audit` step sits before Pint and Pest in the same job, so the advisory skips both. Only `pest-pgsql` still gives a signal. Every push to `master` deploys through the Coolify webhook regardless. Fix: move the audit into its own job, and deploy from a workflow step after both test jobs pass (or turn on Coolify's wait for checks).
4. Morning message. `SendDailyCoaching` sends to every `channelIdentities` row through the one bound `ChatChannel` (Telegram). `log:simulate` creates a `simulate` identity whose `external_id` is the user id, so anyone who ran the simulator gets a daily send to Telegram chat id "1" (or their id). Fix: route by `identity->provider` and skip providers without an adapter. While there, pull the shared "ask the coach and store the turn" steps out of `SendDailyCoaching` and `AnswerCoachQuestion`, which repeat each other line for line.
5. Spend. `AI_MONTHLY_TOKENS_PER_USER=0` turns `CoachBudget` off, and `config/ai.php` has no prices, so `ai:usage` cannot put money on a model switch. `AsksTheCoach` matches any `?`, so "squat 5x5 100?" costs a full coach call. Fix: a non-zero default cap, prices for the models in use, and a narrower question rule. Do this before n38 moves the chat job to a bigger model.
6. Framework. Follow `docs/session-kickoff.md` (`composer update laravel/framework`, both suites) and raise the constraint to `^13.40`. laravel/ai is 1.2 against 1.4 and sanctum one minor behind; bump those after the adapter tests in item 10.

## Direction

Grounded in the direction, rpg and method-card docs of 2026-11-14. Nothing here goes against what those docs rejected. Efforts are coarse.

1. Coach identity as data first (S). `coach_turns` has no persona column, and there is no `/coach` command. Add `persona` (backfill `lt_surge`, the only coach that has spoken), name the coach on answers, label turns in `CoachContext::recentTurns`, then `/coach`. "Ask all three" needs a rule for the 30-a-day cap. This is n39 and the direction doc's first item.
2. Store the coach context with each turn, and a `coach:try` that replays real turns on two models side by side (S to M). Today the context is rebuilt from live data, so last week's questions cannot be replayed as they were. Do this before n38 flips `AI_CHAT_MODEL`. It moves n41 ahead of n38.
3. Plan memory, step 1 (S). The morning brief is saved as `question`, so the next call shows it to the coach as `they_asked`, and both the brief and the plan are cut to 600 characters (`app/Coach/CoachContext.php:149-159`, `config/coach.php:18`). The coach sees a shortened copy of its own plan, labelled as something the person asked. That likely explains "the same plan three days running". Step 1: show daily turns as `you_suggested` with the full plan. Later steps: store the plan's exercises and match the next 24 to 48 hours of logs to it (n40, n42).
4. e1RM and next load in PHP (M). The brief asks the model to do the 2.5 kg step (`app/Actions/Coach/SendDailyCoaching.php:28`), against "PHP decides, the model talks". No e1RM code exists. One `EstimatedOneRepMax` and one `NextLoad` metric feed n40, method card 3, Surge's stat and the app's line per lift. Needs `repair.php` and a canonical exercise key first; spike it read-only over the real logs.
5. Goals that get saved (M). `goal_description`, `goal_deadline` and `target_weight_kg` exist, but only `PUT /api/profile/trainer` writes them and no client calls it. A goal sent in Telegram becomes a general log. A confirm-then-save step ("Save as a goal: squat 100 by 1 Dec? yes / no") gives the bosses their data. Decide user columns or a `goals` table first.
6. The app's coach card (M, blocked on HTTPS). The API already has limitation updates the app type drops, the persona write and every profile version. First settle the two old doors: `/api/trainer/chat` still runs `TrainerAgent` with nutrition, and `POST /api/log` returns 422 for anything that is not a log.

Order by leverage: 1, 2, 3, 4, 5, 6. The Sunday review follows 4. The shadow classifier and the Signal adapter stay parked.
